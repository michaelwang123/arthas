## 战略思考

```
Hub 之前：用户必须有分享码才能用 Arthas（工具属性）
Hub 之后：用户可以"随便逛逛"（社区属性）

关键转变：
  • 从"被动使用"到"主动浏览"
  • 从"1v1 工具"到"多对多社区"
  • 从"用完即走"到"没事就来"（但仍保持轻量）

设计原则：
  • 所有功能必须符合 Arthas 核心价值（无注册、E2EE、轻量、阅后即焚）
  • Hub 功能应利用现有基础设施（房间过期、文件传输、语音消息、OpenClaw）
  • 给人一个"打开 Hub 的理由"
```

## 功能规划

### 一、用户增长类 — 让人主动来 Hub

#### 1.1 随机配对聊天 (Random Match)

```
点击按钮 → 系统从当前在线的人中随机匹配一位
→ 自动创建临时 1v1 加密房间 → 聊完就走
```

**为什么适合 Arthas：**
- 无需注册 + E2EE + 阅后即焚 = 天然的"加密版 Omegle"
- Omegle 关闭后市场有空白，"加密随机聊天"有传播力

**技术方案：**
- 服务端维护匹配队列（FIFO 或兴趣标签配对）
- 配对成功后自动创建房间、生成密钥、双方加入
- 可选：兴趣标签（#tech #music #random）影响匹配
- 房间默认 30min 过期 + 阅后即焚

**实现要点：**
- [ ] 服务端匹配队列 API（`/api/hub/match`）
- [ ] 匹配等待 UI（动画 + 预计等待时间）
- [ ] 匹配成功后自动跳转到房间
- [ ] 超时处理（60s 未匹配提示稍后再试）
- [ ] 举报/拉黑机制（基于 IP 或浏览器指纹，不需要账号）

**预估工作量：** 3-5 天

#### 1.2 每日话题房间 (Daily Topic) ✅ 已完成（2026-06-05）

```
系统每天自动创建一个带话题的公开房间
→ 24h 过期自动销毁 → 第二天新话题
```

**为什么适合 Arthas：**
- 利用现有房间过期机制，几乎零新基础设施
- 给人"每天来看看"的理由（类似 Wordle 的每日仪式感）
- 话题驱动讨论，降低"进入一个陌生房间"的心理门槛

**话题池示例：**
- "推荐一个你离不开的 CLI 工具"
- "你最近发现了什么有趣的开源项目？"
- "如果只能保留 3 个 App，你选哪些？"
- "分享一个你的 unpopular tech opinion"
- "今天你学到了什么新东西？"

**技术方案：**
- Cron job（每天 UTC 0:00）创建房间
- 话题池（JSON 文件 / 数据库），循环或随机抽取
- Hub 首页置顶"今日话题"卡片（特殊样式 + 倒计时）
- 可扩展：用户投稿话题 → 审核后加入池

**实现要点：**
- [x] 话题池数据文件（`internal/dailytopic/topics.json`，30+ 条预设话题）
- [x] 服务端调度器（1h ticker + 幂等创建 + 24h 过期 + 标记为"每日话题"）
- [x] Hub 首页"今日话题"置顶卡片 UI（DailyTopicCard 组件 + 倒计时）
- [x] `--disable-daily-topic` 配置开关（flag + 环境变量）

**预估工作量：** 1-2 天

#### 1.3 漂流瓶 (Message in a Bottle)

```
写一条加密消息投入"漂流瓶池"
→ 随机某人领取 → 一人一瓶，领了就消失
→ 可选：回复漂流瓶（系统创建临时 1v1 房间）
```

**为什么适合 Arthas：**
- 阅后即焚的极致体现：一条消息只有一个人能看到，看完就没了
- 匿名 + 一次性 = 低心理门槛的表达出口
- 有"收到惊喜"的愉悦感，增加回访率

**技术方案：**
- 服务端维护"瓶池"（加密消息队列）
- 投瓶：用户输入消息 → 客户端用临时密钥加密 → 存入队列（附带解密密钥）
- 捞瓶：用户请求 → 服务端随机分配一个瓶 → 返回密文+密钥 → 客户端解密
- 领取后从队列删除（一人一瓶）
- 可选回复：点击"回复这个瓶子" → 创建临时房间 → 原作者收到通知（如果还在线）

**安全考虑：**
- 瓶子在服务端是加密存储的（但服务端持有密钥——与 Hub 公开房间安全模型一致）
- 或：瓶子明文存储（反正只存在很短时间），保持实现简单
- 需要防刷：每人每小时最多投 3 瓶、捞 5 瓶

**实现要点：**
- [ ] 漂流瓶 API（`POST /api/hub/bottle` 投瓶，`GET /api/hub/bottle` 捞瓶）
- [ ] 瓶子存储（内存队列 or Redis，设 TTL 24h 自动过期）
- [ ] Hub 页面"漂流瓶"入口（投瓶 / 捞瓶 两个按钮）
- [ ] 投瓶 UI（简单文本输入 + 字数限制 280 字）
- [ ] 捞瓶 UI（开瓶动画 + 展示内容 + 回复按钮）
- [ ] 防刷限流

**预估工作量：** 2-3 天

### 二、社交互动类 — 让人待着不走

#### 2.1 加密文字游戏

```
在 Hub 开"狼人杀"/"谁是卧底"/"Truth or Dare"房间
→ OpenClaw AI Agent 担任主持人
→ E2EE 保证游戏公平（服务器无法偷看角色分配）
```

**为什么适合 Arthas：**
- E2EE 天然保证游戏公平性（服务器不知道谁是狼人）
- 利用现有 reaction 做投票、reply 做讨论
- OpenClaw Agent 做主持人 = 无需真人组织
- "加密狼人杀"本身就有话题性和传播力

**游戏清单（由简到难）：**

| 游戏 | 人数 | 利用现有功能 | 复杂度 |
|------|------|-------------|--------|
| Truth or Dare | 2+ | 文本消息 | ⭐ |
| 你画我猜（文字版） | 3+ | 文本消息 | ⭐⭐ |
| 谁是卧底 | 4+ | 加密私信 + 投票(reaction) | ⭐⭐⭐ |
| 狼人杀 | 6+ | 加密角色分配 + 投票 + 阶段控制 | ⭐⭐⭐⭐ |

**技术方案：**
- 游戏主持人 = OpenClaw Agent（加入房间，分配角色，计票，宣布结果）
- 角色分配：Agent 对每个玩家单独发送加密消息（只有该玩家能解密）
- 投票：利用 reaction 功能（👍 = 投票），Agent 计票
- 阶段控制：Agent 发系统消息宣布"天黑请闭眼" / "投票开始"

**实现要点：**
- [ ] 游戏 Agent 框架（基于 openclaw-channel，扩展游戏逻辑）
- [ ] 游戏模板配置（规则、人数、阶段定义）
- [ ] Hub 中"游戏房间"标签分类
- [ ] "一键开游戏"按钮（选择游戏类型 → 创建房间 + 自动邀请 Agent）

**预估工作量：** 1-2 周（从最简单的 Truth or Dare 开始）

#### 2.2 异步语音广场 (Voice Square)

```
一个公开房间，大家用 Push-to-Talk 录一段话丢进去
→ 像加密版的"语音留言板"/ 异步播客
```

**为什么适合 Arthas：**
- 复用现有加密语音消息基础设施，零新开发
- 异步参与不需要同时在线（比实时语音门槛低）
- 差异化："加密的语音留言板"市面上没有

**玩法：**
- 设定主题："用一分钟推荐一首歌"
- 每条语音限时 60s（已有限制）
- 可以用 reaction 给喜欢的语音消息点赞
- 每天/每周一个新话题（可与"每日话题"联动）

**实现要点：**
- [ ] Hub 中标记"语音广场"类型的房间（UI 上突出 🎙️ 图标）
- [ ] 语音广场模板（预设：允许语音、禁止文字、设定话题）
- [ ] 热门语音置顶（按 reaction 数排序）

**预估工作量：** 1 天（主要是 UI 和模板，核心功能已有）

#### 2.3 匿名树洞

```
一个永驻 Hub 房间，任何人进来说句话就走
→ 无身份、无历史、无追踪
```

**为什么适合 Arthas：**
- 无注册 + 每次进入生成新临时身份 = 真正的匿名
- 阅后即焚 = 说过的话不留痕
- 场景：情绪出口、匿名求助、不方便在社交平台说的话

**与普通房间的区别：**
- 不显示昵称（或显示随机 emoji 代号，如 🐱、🌊、🎨）
- 每次进入分配新身份（不可追踪同一人的多条消息）
- 强制阅后即焚（60s）
- 不支持 reply/reaction（减少身份关联）

**实现要点：**
- [ ] "匿名模式"房间配置项
- [ ] 随机 emoji 昵称生成器
- [ ] Hub 首页"树洞"入口（特殊 UI 样式，暗色调）
- [ ] 服务端保证该房间永驻（不过期、不销毁）

**预估工作量：** 1-2 天

### 三、工具/实用类 — 解决真实需求

#### 3.1 开发者 Office Hours

```
开源项目维护者在 Hub 开"每周三下午3点在线答疑"
→ 设好过期时间，到点自动销毁
```

**为什么适合 Arthas：**
- 开源社区的低成本互动方式（不需要 Discord server、不需要注册）
- 临时性 + 无注册 = 参与门槛极低
- 可结合标签：`#rust` `#golang` `#react` `#devops`

**扩展：定时房间 (Scheduled Rooms)**
- 提前创建一个未来开放的房间
- "明天晚上8点开始，讨论 Rust async"
- 到时间才能进入
- 类似 Twitter Spaces 的预告功能

**实现要点：**

- [ ] Hub 中"即将开始"分类（显示倒计时）
- [ ] 日历视图（一周内的预定房间）
- [ ] 到时间自动通知（如果用户收藏了该房间）

**预估工作量：** 2-3 天

#### 3.3 公共 AI 助手房间

```
Hub 常驻一个 OpenClaw AI Agent 房间
→ 任何人加入就能和 AI 对话
→ 全程 E2EE，连 AI 对话都不被监控
```

**为什么适合 Arthas：**
- 已有 OpenClaw 插件，只需配置一个常驻 Agent
- 展示"连 AI 对话都是 E2EE"的独特卖点
- 场景：匿名问 AI 敏感问题（健康、法律、心理），不留痕迹
- 增长逻辑："唯一一个和 AI 聊天都不被监控的地方"

**技术方案：**
- 部署一个常驻 OpenClaw Agent（持有 LLM API key）
- Agent 自动创建/维护一个公开 Hub 房间
- 新用户加入时 Agent 发送欢迎消息
- 多用户同时对话：Agent 区分上下文（按 sender 分 session）

**实现要点：**
- [ ] Agent 自动创建/恢复 Hub 房间的逻辑
- [ ] 多用户上下文隔离
- [ ] 使用量限制（防止滥用，每人每天 N 条）
- [ ] Hub 首页"AI 助手"特殊入口（🤖 图标 + 在线状态指示）

**预估工作量：** 2-3 天

### 四、技术探索类 — 展示可能性

#### 4.1 Hub 联邦 (Federated Hub)

```
不同自托管实例的 Hub 互相发现
→ A 服务器用户能看到 B 服务器的公开房间并跨服务器加入
→ 去中心化网络效应
```

**为什么有意思：**
- 类似 Mastodon 的联邦模型
- 每个自托管实例都是网络的一个节点
- 解决"单服务器用户太少"的冷启动问题

**技术方案（概念）：**
- 服务器间通过 ActivityPub 或自定义协议交换房间元数据
- 跨服务器加入：客户端直连目标服务器 WebSocket
- 信任模型：服务器管理员可选加入/退出联邦

**难度：** ⭐⭐⭐⭐⭐（远期规划）

---

#### 4.2 房间热度/活跃排行

```
Hub 首页展示"此刻最活跃的房间"
→ 基于在线人数、消息频率排序
```

**为什么可行：**
- 服务器虽不看消息内容，但知道每个房间的连接数和消息量（元数据）
- 给人"这里有活人在聊"的感觉，降低加入门槛

**排序维度：**
- 🔥 最活跃（最近 5 分钟消息量最高）
- 👥 最多人（当前在线人数排序）
- 🆕 最新（刚创建的房间）
- ⭐ 推荐（编辑精选/置顶）

**实现要点：**
- [ ] 服务端统计各房间活跃度（滑动窗口计数）
- [ ] Hub API 返回排序字段
- [ ] 前端排序切换 UI（Tab 或下拉）
- [ ] "此刻 N 人在线"全局统计

**预估工作量：** 1-2 天

---

#### 4.3 定时房间 (Scheduled Rooms)

```
提前创建一个未来开放的房间
→ "明天晚上8点开始" → 到时间才能进入
→ 类似 Twitter Spaces 的预告功能
```

**技术方案：**
- 房间增加 `startsAt` 字段
- 未到时间加入 → 返回"房间尚未开放 + 开放时间"
- Hub 中"即将开始"标签页
- 可选：到时间前 15 分钟发送提醒（需要通知机制）

**实现要点：**
- [ ] 协议扩展（ROOM_CREATE 增加 startsAt 参数）
- [ ] 服务端加入时间检查
- [ ] Hub "即将开始"分类 + 倒计时 UI
- [ ] 创建房间表单增加"预定开始时间"选项

**预估工作量：** 2 天

## 成功指标

| 指标 | 目标 | 衡量方式 |
|------|------|----------|
| Hub 日活 | 从 0 到 50+ | 服务端统计每日独立 Hub 访问 |
| 自然回访率 | > 30% 次日留存 | 同一浏览器指纹次日再访问 Hub |
| 房间创建数 | 每日 10+ 个 Hub 房间 | 服务端统计 |
| 随机匹配成功率 | > 80%（60s 内配对） | 匹配队列统计 |
| 每日话题参与人数 | > 10 人/天 | 房间成员数峰值 |

## 不做的事情

| 反模式 | 理由 |
|--------|------|
| 用户注册/个人主页 | 违背"无需注册"核心价值 |
| 永久房间/频道 | 违背"临时/阅后即焚"定位（树洞是唯一例外） |
| 关注/粉丝体系 | Arthas 不是社交平台 |
| 房间内广告/推广 | 破坏信任，与 E2EE 精神矛盾 |
| 复杂的身份/声望系统 | 增加使用门槛，违背轻量原则 |
