# Arthas 路线图

> 更新：2026-05-19  
> 定位：加密版 AirDrop + 临时聊天 — 安全交换信息，用完即走  
> 架构：事件驱动，服务器纯中转（零知识）  
> 加密：Web Crypto API + AES-256-GCM  
> 技术栈：Go · WebSocket · MessagePack · React · Vite

---

## 产品定位

```
Arthas ≠ Signal 的替代品（Signal 做长期通信）
Arthas = "我需要和某人安全地交换一些信息，用完即走"

核心价值：
  • 无需注册，打开即用
  • 端到端加密，服务器零知识
  • 阅后即焚，房间销毁密文消失
  • 轻量自托管，一行命令部署
```

## Phase 8：安全升级

```
目标：从"够用的安全"到"专业级安全"
时间：持续迭代
优先级：🔵 低（当前方案已足够安全）
```

| 升级 | 复杂度 | 收益 | 优先级 |
|------|--------|------|--------|
| 加密 typing 状态 | 低 | 减少元数据泄露 | P1 |
| 消息签名 (Ed25519) | 中 | 防服务器伪造消息 | P2 |
| 公钥缓存 LRU 淘汰 | 低 | 长期房间内存优化 | P2 |
| SAS 验证 (Short Auth String) | 中 | 验证对方身份，防中间人 | P2 |
| 密钥轮换 (踢人后) | 中 | 被踢成员无法解密后续消息 | P2 |
| Double Ratchet (前向保密) | 高 | 密钥泄露不影响历史消息 | P3 |
| WebRTC P2P (可选) | 高 | 完全绕过服务器 | P3 |

> **Phase 8 后续迭代备忘（来自 security-upgrade spec 评审）：**
> - **publicKeyMap 内存增长**：当前设计中成员离开后公钥仍留在 map 中。对于临时聊天场景（小规模、短生命周期）不是实际问题。如果未来支持大规模/长期房间，需添加 LRU 淘汰策略（按 `firstSeen` 时间戳清理超过 N 分钟未活跃的条目）。
> - **签名密钥轮换**：Phase 8.1 采用 TOFU 模型，密钥变更时仅显示警告。后续可引入 SAS 验证让用户主动确认对方身份，从"信任首次"升级为"可验证信任"。

**Done when：** 通过第三方安全审计

## 战略原则

### ✅ 坚持做的

| 原则 | 理由 |
|------|------|
| 无需注册 | 核心卖点，降低使用门槛 |
| 阅后即焚 | 核心卖点，差异化定位 |
| 服务器零知识 | 安全基石，不可妥协 |
| 轻量简洁 | 用完即走的工具，不是社交平台 |
| 开源透明 | 建立信任，安全可审计 |

### ❌ 不做的

| 反模式 | 理由 |
|--------|------|
| 用户注册/账号体系 | 杀死"无需注册"核心价值 |
| 消息持久化/历史记录 | 杀死"阅后即焚"核心价值 |
| 原生 App (iOS/Android) | PWA 足够，维护成本太高 |
| 过度工程化后端 | 它就是个 relay，保持简单 |
| 急着加 Double Ratchet | 对临时聊天收益不大，复杂度极高 |
| 社交功能（好友/群组/动态） | 偏离定位，变成另一个 IM |
