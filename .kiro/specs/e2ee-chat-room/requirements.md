# 需求：端到端加密实时聊天室

## 概述

将现有的游戏项目重构为一个端到端加密 (E2EE) 实时聊天应用。用户可以创建临时聊天房间，通过分享密钥邀请伙伴加入，所有消息在客户端加密后传输，服务器仅做密文中转。

## 用户故事

### US-1: 创建聊天房间

作为用户，我想要一键创建一个临时聊天房间，以便开始私密对话。

**验收标准：**
- AC1: 输入昵称（1-20 字符），点击"创建房间"，< 500ms 返回分享码
- AC2: 分享码格式为 `{roomId}:{base64url(roomKey)}`，其中 roomId 为 NanoID 21 字符，roomKey 为 AES-256 (32 bytes) 的 base64url 编码（43 字符）
- AC3: 创建者自动加入房间，成为第一个成员
- AC4: 每次创建生成独立的 roomKey，即使同一用户连续创建多个房间
- AC5: 昵称为空或超过 20 字符时，按钮禁用并显示提示

### US-2: 加入聊天房间

作为用户，我想要通过分享码加入朋友的聊天房间。

**验收标准：**
- AC1: 输入分享码和昵称，点击"加入房间"
- AC2: 客户端解析分享码，提取 roomId 和 roomKey（roomKey 不发送给服务器）
- AC3: 服务器验证 roomId 存在后返回当前成员列表
- AC4: 加入成功后，房间内所有人收到 MemberJoined 通知
- AC5: 分享码格式错误时，显示"分享码无效"提示
- AC6: roomId 对应的房间不存在（已销毁）时，显示"房间不存在或已关闭"
- AC7: 房间已满（50 人）时，显示"房间已满，无法加入"
- AC8: 支持通过 URL hash 路由 `/#/join/{shareCode}` 自动填充分享码（不引入 react-router，使用 hash routing）

### US-3: 端到端加密聊天

作为用户，我想要发送加密消息，确保只有房间内的人能读取。

**验收标准：**
- AC1: 输入消息，按 Enter 或点击发送按钮
- AC2: 客户端使用 roomKey + AES-256-GCM + 随机 96-bit IV 加密消息
- AC3: 加密后的 {iv, ciphertext} 通过 WebSocket 发送给服务器
- AC4: 发送者本地**乐观渲染**：发送即显示在消息列表（无需等待服务器确认），标记为"已发送"。若 WebSocket 断开导致实际未送达，不单独标记"发送失败"（V1 简化设计，断线时 US-7 AC2 横幅已提供全局提示；V2 可考虑加"发送失败，点击重试"）
- AC5: 服务器原样转发密文给房间内其他成员（不含发送者自己）
- AC6: 接收方使用 roomKey + IV 解密密文，显示明文
- AC7: 服务器日志和内存中不存在任何明文消息内容
- AC8: 解密失败时（密钥不匹配），显示"无法解密此消息"占位符，不崩溃
- AC9: 消息长度限制 1-500 字符，超出时输入框阻止输入并提示
- AC10: 消息支持 UTF-8 全字符集（含 emoji）
- AC11: 消息频率限制：同一用户 10 秒内最多发送 10 条，超出时提示"发送过快"
- AC12: 消息顺序以服务器接收时间为准，服务器在 RelayMessage 中附带时间戳 `t` 作为排序依据

### US-4: 实时成员管理

作为用户，我想要看到谁在房间里，谁加入了，谁离开了。

**验收标准：**
- AC1: 显示在线成员列表（昵称 + 颜色标识）
- AC2: 颜色基于成员 ID（服务器分配）hash 分配，确保即使昵称相同也能通过颜色区分；昵称旁显示短 ID 后缀（如 `Alice#3f`）以消除歧义
- AC3: 新成员加入时，列表实时更新 + 系统消息提示"xxx 加入了房间"
- AC4: 成员离开时，列表实时移除 + 系统消息提示"xxx 离开了房间"
- AC5: 显示"正在输入"状态（xxx 正在输入...），2 秒无输入后自动取消
- AC6: "正在输入"状态为未加密元数据（服务器可见），这是已知的隐私权衡
- AC7: 系统消息（加入/离开/房间关闭）为服务器明文广播，不经过 E2EE 加密（因为由服务器生成，非用户消息）

### US-5: 分享密钥

作为房间创建者，我想要方便地分享房间密钥给朋友。

**验收标准：**
- AC1: 聊天室内显示"分享"按钮，点击后展示分享码
- AC2: 一键复制分享码到剪贴板，复制成功后显示"已复制"反馈
- AC3: 可选：生成分享链接 `https://domain.com/#/join/{shareCode}`
- AC4: 分享码有效期 = 房间存活期（所有人离开后失效）
- AC5: 分享码无法撤销或更换（设计限制，已知安全边界）

### US-6: 房间自动销毁

作为系统，当所有成员离开房间后，房间应自动销毁。

**验收标准：**
- AC1: 最后一个成员离开（主动离开或断线超时）时，房间从内存中删除
- AC2: 房间销毁后，使用相同分享码加入返回"房间不存在"
- AC3: 无持久化，无法恢复已销毁的房间
- AC4: 房间销毁前，向所有在线成员发送 RoomClosed 通知

### US-7: 错误处理与降级

作为用户，我想要在异常情况下获得清晰的反馈，而不是无响应或崩溃。

**验收标准：**
- AC1: WebSocket 连接失败时，显示"连接中..."状态，自动重试（指数退避：1s, 2s, 4s, 8s, max 30s）
- AC2: 连接断开时，显示"连接已断开，正在重连..."横幅
- AC3: 重连成功后，如果之前在房间中，自动尝试重新加入（使用当前标签页内存中缓存的 roomId）
- AC4: 重新加入失败（房间已销毁）时，显示"房间已关闭"并返回首页
- AC5: 断线期间的消息不可恢复（无持久化），重连后显示"您断线期间可能错过了消息"提示
- AC6: 服务器返回 Error 消息时，根据 error code 显示对应中文/英文提示
- AC7: 任何未预期的异常不导致页面白屏，使用 ErrorBoundary 兜底
- AC8: roomKey 仅存于当前标签页内存（Zustand store），页面刷新或关闭标签页 = 离开房间（密钥丢失）

## 非功能需求

### NFR-1: 安全性
- 消息使用 AES-256-GCM 端到端加密
- 服务器零知识设计，不持有 roomKey，不解析消息内容
- 传输层使用 WSS (TLS 1.3)
- 每条消息使用随机 96-bit IV（crypto.getRandomValues）
- 服务器可见的元数据：roomId、成员 ID/昵称、消息时间戳、typing 状态
- 服务器不可见：消息明文、roomKey

### NFR-2: 性能
- 消息端到端延迟 < 100ms（局域网）
- 单房间支持 50 人同时在线
- 服务器支持 100+ 并发 WebSocket 连接
- 加密/解密操作 < 5ms（Web Crypto API 硬件加速）
- 前端消息列表最多保留 200 条，超出后静默移除最早的消息（不显示提示）

### NFR-3: 可用性
- 无需注册，打开即用
- 支持现代浏览器（Chrome 90+, Firefox 90+, Safari 15+, Edge 90+）
- 断线自动重连（指数退避）
- 响应式布局（PC 优先，移动端可用）

### NFR-4: 消息格式约束
- 消息长度：1-500 字符
- 字符集：UTF-8（含 emoji、多语言）
- 频率限制：10 条/10 秒/用户（客户端 + 服务器双重校验）
- 昵称长度：1-20 字符，允许字母、数字、中文、emoji

## 安全边界

### 已知安全限制（设计决策）

| 限制 | 说明 | 风险等级 | 缓解措施 |
|------|------|----------|----------|
| 分享码不可撤销 | 一旦分享码泄露，任何人可加入直到房间销毁 | 中 | 所有人离开即销毁；后续可加"踢人"功能 |
| 无前向保密 (PFS) | 如果 roomKey 泄露，所有历史消息可解密 | 低 | 消息不持久化，房间销毁后密文消失 |
| Typing 状态未加密 | 服务器可见谁在打字 | 低 | 不含消息内容；后续可改为加密 typing |
| 无消息持久化 | 断线期间消息丢失 | 中 | 明确告知用户；后续可加本地缓存 |
| 无身份验证 | 任何人可用任意昵称 | 低 | 临时聊天场景可接受；后续可加密码保护 |
| NanoID 碰撞 | 21 字符 NanoID 碰撞概率 ~10^-36 | 极低 | 可忽略；服务器创建时检查唯一性 |

### 信任模型

```
信任：
  - 浏览器环境（Web Crypto API 实现正确）
  - 用户通过安全渠道分享密钥（如面对面、加密 IM）

不信任：
  - 服务器（零知识设计）
  - 网络传输（TLS 保护）

假设：
  - 用户设备未被恶意软件控制
  - 浏览器未被篡改
```

## 正确性属性 (Correctness Properties)

以下属性可用于自动化测试验证系统正确性：

| ID | 属性 | 验证方式 |
|----|------|----------|
| P1 | 任意明文 M，encrypt(key, M) 后 decrypt(key, ...) = M | 单元测试：随机字符串往返 |
| P2 | 不同 roomKey 无法解密对方消息（decrypt 抛出异常） | 单元测试：交叉解密失败 |
| P3 | 同一消息加密两次产生不同密文（IV 随机性） | 单元测试：两次加密结果不等 |
| P4 | 房间成员数 = 0 时，房间不存在于服务器内存 | 集成测试：所有人离开后查询 |
| P5 | 服务器进程内存中不存在任何 roomKey 值 | 代码审查 + 集成测试 |
| P6 | RelayMessage 中的 ciphertext 与 SendMessage 中的完全一致（字节级） | 集成测试：对比发送和接收 |
| P7 | 消息顺序：服务器按接收顺序转发，RelayMessage 中的时间戳 `t` 单调递增（单房间内） | 集成测试：多客户端并发发送，验证 `t` 递增 |
| P8 | 房间人数 ≤ 50（超出时拒绝加入） | 压力测试 |

## 技术约束

- 前端：React 18 + TypeScript + Vite 5 + Zustand + Tailwind CSS
- 加密：Web Crypto API (AES-256-GCM)，不引入第三方加密库
- 协议：WebSocket + MessagePack (二进制序列化)
- 后端：Go 1.22 + gorilla/websocket
- 无数据库，纯内存状态
- 密钥生成：NanoID (roomId, 21 chars) + crypto.getRandomValues (roomKey, 32 bytes)
- 路由：前端使用 hash routing（`/#/join/{code}`），不引入 react-router
- 现有代码需完全重写（当前是游戏服务器，与聊天室无关）

## 术语表

| 术语 | 定义 |
|------|------|
| E2EE | End-to-End Encryption，端到端加密 |
| roomId | 房间唯一标识符，NanoID 生成，21 字符 |
| roomKey | 房间对称加密密钥，AES-256，32 bytes |
| 分享码 | `roomId:base64url(roomKey)` 格式的字符串 |
| IV | Initialization Vector，初始化向量，96-bit 随机 |
| AEAD | Authenticated Encryption with Associated Data |
| Relay | 服务器中转模式，原样转发密文 |
| 零知识 | 服务器不持有解密能力，无法读取消息内容 |
